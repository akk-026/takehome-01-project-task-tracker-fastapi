# Schema

The database is managed by SQLAlchemy: SQLite is used locally and PostgreSQL is used for a hosted
deployment. The table structure is the same in both environments. IDs are integer primary keys;
timestamps are timezone-aware datetimes generated by the database unless stated otherwise.

- `users`: `id` integer; `name` varchar(120); unique, indexed `email` varchar(255); `password_hash`
  varchar(255); `role` enum (`MANAGER` or `MEMBER`); and `created_at` datetime.
- `projects`: `id` integer; unique, indexed `key` varchar(12); `name` varchar(160);
  `description` varchar(2,000); indexed `owner_id` foreign key to `users`; non-null `archived`
  boolean; and `created_at`/`updated_at` datetimes.
- `project_members`: `project_id` and `user_id` foreign keys, together the composite primary key.
  This is the project-membership many-to-many table.
- `tasks`: `id` integer; indexed `project_id` foreign key; `title` varchar(300); `description`
  varchar(4,000); `priority` enum (`LOW`, `MEDIUM`, `HIGH`, `CRITICAL`); nullable `due_date` date;
  `status` enum (`BACKLOG`, `IN_PROGRESS`, `IN_REVIEW`, `BLOCKED`, `DONE`); nullable `blocked_from`
  enum; non-null `deleted` boolean; `created_at`/`updated_at` datetimes; and nullable
  `completed_at` datetime, populated only while the task is Done.
- `task_assignees`: `task_id` and `user_id` foreign keys, together the composite primary key. This is
  task assignment's many-to-many table.
- `task_blockers`: `task_id` and `blocking_task_id` foreign keys to `tasks`, together the composite
  primary key. This is the self-referential blocker many-to-many table.
- `task_activities`: `id` integer; indexed `task_id` foreign key; nullable `actor_id` foreign key;
  `action` varchar(32); nullable `field_name` varchar(64); nullable `old_value`, `new_value` and
  `comment` text; and immutable `created_at` datetime. It represents the timeline; comments are
  activity rows rather than a separately editable resource.
- `task_alert_dismissals`: `id` integer; indexed `task_id` and `user_id` foreign keys; and
  `dismissed_at` datetime. A unique `(task_id, user_id)` constraint makes dismissal idempotent;
  rows are deleted when that task's due date changes.

A project owns many tasks and has one owner. A task belongs to exactly one project. Membership,
assignment, and blockers are many-to-many relationships expressed with junction tables and database
foreign keys. Project keys and junction-table pairs are unique at the database level. The application
enforces role permissions, project visibility, same-project blockers, project-membership assignment,
legal lifecycle moves, and the rule that unfinished blockers prevent completion.

Database constraints cover primary keys, unique user emails and project keys, unique junction pairs,
the alert-dismissal pair, non-null fields and foreign-key relationships. Application code enforces
permissions and visibility, same-project blockers, project-membership assignment, legal lifecycle
moves, unfinished-blocker completion checks, soft deletion and append-only history. A database
constraint cannot conveniently express these rules without making ordinary application writes much
less clear.

The intentionally denormalised fields are `completed_at` (for stable completion reporting),
`blocked_from` (to restore a blocked task without inferring its previous state), and the human-readable
old/new values on activity rows (so the timeline remains understandable after a related record is
renamed or no longer visible). Task activity rows are write-once application records: no API endpoint
updates or deletes them. Application write paths append the actor and before/after values in the same
transaction that changes a task.

Overdue alert eligibility is calculated from task status and due date rather than stored as a second
task state. The dismissal table is intentionally per user because every assignee controls their own
alert, while a revised deadline clears all earlier dismissals.

The finder queries tasks with joins only for project visibility, and filters, sorts, counts, paginates,
and exports on the server. At 100× the data, the first improvements would be database indexes for
task project/status/due date/updated time plus indexes supporting membership and assignment lookups.
The dashboard would also benefit from indexes for active task status and completion timestamps.
